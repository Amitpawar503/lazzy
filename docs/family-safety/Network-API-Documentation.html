Optimization — can we collapse the Network surface?

The check-in / SOS / alarm / device-status endpoints share the same event shape. Modelling them as one Safety Event resource with eventType + action enums (as on the upstream BFF) collapses ~15 event endpoints into ~5 — same coverage, fewer contracts, one state machine.

GroupTodayOptimisedSave
Check-in create / status / response3 POSTPOST /api/v1/safety-event (eventType=CHECK_IN) + POST /api/v1/safety-event/{id}/action (action=RESPONSE|DISMISS|PAUSE|RESUME)−2
SOS create / cancel / update3 POSTsame safety-event + action (action=CANCEL|ACKNOWLEDGE|RESOLVE)−2
Alarm incoming / outgoing / sos-kill3 POSTfolds into safety-event (eventType=FRAUD/ALARM) + action=NOTIFY|KILL−2
Check-in get + SOS get2 GETGET /api/v1/safety-event?scope=id|familyId|msisdn + type−1
Device status get + safety report get2 GETGET /api/v1/safety-event?view=DEVICE_STATUS|SAFETY_REPORT−1
member add / update / delete / role4 POSTresource style: POST /members, PUT /members/{id}, POST /members/{id}/status(action)−1

Net: 23 → ~15 Network endpoints. Family/Member CRUD can also go resource-style (POST create, PUT update, POST …/status for role/delete) — removing the mislabelled member/role/update "Delete" summary and any need for a separate delete verb.

Gaps to close with Network: G1 add GET /api/v1/family/getByMsisdn?msisdn= (MSISDN→familyId) · G2 membershipStatus only Active/Inactive — add invite lifecycle states or let the BFF own them · G6 role enum SPONSER → SPONSOR? · G7 GEOFENCE/INACTIVITY have no Network owner (deck excludes geofencing + device-status alerts) · Confirm Alarm/Device-Status are REST vs Kafka-only, and the Safety-Report schema (TBD).
